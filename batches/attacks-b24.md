## A1
TOPIC: History pseudostates resume a stale substate after a GLOBAL detour without re-running the guard that first admitted it
SCENARIO: In QUOTE.LOAN_TERMS the caller asks "who is this company again?" GLOBAL request_caller_identity plays the fixed answer, then returns to QUOTE through a (deep) history state, as is normal for detours. During the detour the caller also says "actually we're the Fresno house, not the Bay one", setting jurisdiction_changed. History re-enters QUOTE.LOAN_TERMS directly. The guard that chose LOAN_TERMS (lead-gen-mode false, financing allowed in this jurisdiction) was evaluated under the old jurisdiction and never re-runs. The agent quotes financing where only lead-gen mode is allowed.
WHY IT BREAKS: History restores where you were, not whether you may still be there. Entry guards are checked only on the original edge, so every detour-and-return is an unguarded entry. Invariants written as "edges into X require guard G" pass while history bypasses G. UML: history re-enters the last active substate, with no guard re-evaluation (UML 2.5 sec. 14.2.3.4.5).

## A2
TOPIC: Timers live in user variables outside the graph, so a timer armed in one state fires after a GLOBAL exit into another
SCENARIO: StateSmith has no built-in timers; the usual pattern arms a timestamp variable on entry and checks it in a `do` handler. READ_BACK arms "silence > 6 s -> re-prompt: shall I send the agreement?" The caller says "my husband just collapsed", sensitive_event exits to the scripted exit. The timer variable is never cleared (READ_BACK's exit action doesn't clear it on this path). In the exit state, the shared `do` handler sees the expired deadline and plays the re-prompt: "Shall I send the agreement now?"
WHY IT BREAKS: The model checker explores control states and events. An armed timer is data, not a state, so a stale timer that leaks across exits is invisible to it. Every GLOBAL exit needs every timer cleared, and nothing checks that. That gap is exactly how a pitch line gets played into an emergency exit.

## A3
TOPIC: Overlapping guards resolved by edge order: first-true-wins quietly picks the sale over the honest exit, and a diagram edit flips the order between releases
SCENARIO: The suitability table returns roof_age=24 (ROOF_FIRST condition) and move_horizon=18 months (NOT_SUITABLE condition). Both outgoing guards from QUALIFY are true. StateSmith takes the first by behavior order. In v14 a designer redrew the edges, and the order prefix changed from 1/2 to 2/1. ROOF_FIRST, which upsells a reroof plus solar, now beats NOT_SUITABLE for every caller who is planning to move. All invariants still pass, because both targets are "legal".
WHY IT BREAKS: The design checks invariants, not guard mutual exclusion or determinism. When guards overlap, the outcome is decided by a priority number edited in a drawing tool. Neither edge breaks a safety property, so the checker passes it, but the policy outcome flips with no test failing and no row changing in the suitability table.

## A4
TOPIC: "Every commit passes READ_BACK" is true but insufficient: the commit gate keys on a question id that is constant across read-backs, so a yes to an old read-back binds new terms
SCENARIO: Read-back #1 says 7.2 kW at a total of $31,400. The caller asks "can we do the smaller one?" The machine backtracks, recomputes 5.8 kW and plays read-back #2. Midway, the caller barges in: "yes, yes, the one you said first." The COMMIT gate checks "short lexical affirm to this read-back question id". Both read-backs use the same fragment and question id, so the gate is satisfied. The slot store now holds 5.8 kW, so the envelope goes out for terms the caller explicitly rejected.
WHY IT BREAKS: The proven invariant is a path property: READ_BACK was visited. The property that matters is a data property: the affirm answers a read-back whose content hash equals the slot-store version that gets committed. Nothing ties the commit to which read-back instance it answers, so the invariant holds while the wrong terms get signed.

## A5
TOPIC: Counters reset on state entry plus data abstraction in the checker mean "clarify once, then fallback" and the call budgets never fire across a two-state ping-pong
SCENARIO: The clarify counter is a per-state variable zeroed in the entry action. The caller's turns alternate between "what?" (QUOTE -> CLARIFY_PRICE) and a dispute_prior_statement detour (re-read the table value, return to QUOTE). Each return re-enters QUOTE and zeroes the counter. The turn budget counts only LOCAL turns, and detours are GLOBAL. For 40 minutes the agent re-reads the price. It never falls back or wraps up, and the caller keeps getting pitched.
WHY IT BREAKS: Model checkers make slot data tractable by abstracting counters away or bounding them, so a counter that never reaches its limit shows up as at most a spurious, dismissed loop, never as a liveness violation. "Every call eventually reaches WRAP_UP" is then proved over an abstraction in which counters always count up.

## A6
TOPIC: GLOBAL exit sequences are not absorbing: root handlers stay live inside the stop/cancel exit, so a second GLOBAL event re-routes an opt-out back toward sales
SCENARIO: The caller says "stop calling me." The stop/DNC exit is a short sequence of states under the root: confirm opt-out, outbox copy, goodbye. Mid-confirmation the caller asks "wait, who is this, is this a real person?" Root request_caller_identity fires (the most general handler), plays the fixed answer and then returns by history to the last sales state, QUOTE. The pitch resumes after a recorded opt-out. Equally, "let me talk to someone" inside the exit triggers request_human, a warm transfer to a closer.
WHY IT BREAKS: The checked invariant is "stop reaches the exit". It is not "after stop, no sales state or transfer to sales is reachable". Exit states inherit the root's GLOBAL transitions like any other state. An opt-out followed by more selling is a revocation violation under the TCPA and TSR (47 CFR 64.1200; 16 CFR 310.4(b)(1)(iii)(A)).

## A7
TOPIC: Vacuous passes after a graph refactor: properties written against state names stay green when those states are split, renamed or bypassed
SCENARIO: The spec says "AG(in COMMIT -> previously READ_BACK)" and "commit tools only enabled in COMMIT". In v15 COMMIT is split into COMMIT_CASH and COMMIT_LOAN for a new lender, and QUOTE gains a fast path straight to COMMIT_LOAN. The old properties still name COMMIT, which is now unreachable, so both hold vacuously. CI shows all invariants passed. COMMIT_LOAN enables the e-sign tool with no READ_BACK on the fast path.
WHY IT BREAKS: Model checkers report a property as satisfied when its antecedent is never reached, unless vacuity checking is turned on. The property list is hand-maintained, while the graph changes every release. No check says "every state with a commit tool is covered by a property", so the safety of each release depends on someone remembering to rename strings.

## A8
TOPIC: An `else` / default branch on a choice point fails open when the policy table gains a value the graph was never generated for
SCENARIO: A suitability choice point covers roof_material values ASPHALT, TILE and METAL, with a mandatory default `else -> QUOTE`. Ops adds SLATE_REQUIRES_ENGINEERING and WOOD_SHAKE_FIRE_ZONE to the versioned policy table. The table's certificate expires and is reissued, but the graph is not regenerated. Every slate or wood-shake roof falls through `else` straight to QUOTE. These are fire-zone homes that should have gone to NOT_SUITABLE or an engineering review. The model check of the unchanged graph still passes.
WHY IT BREAKS: The graph and the policy table are versioned separately. Guards switch on enumerations the table owns, and nothing checks that the switches are exhaustive against the current table. A default branch written for "unusual but fine" silently takes every new category, including the dangerous ones. The checker treats `else` as a legal edge, so this release-time mismatch never shows up.

## A9
TOPIC: Exit and entry actions run on every path across a state boundary, so effects placed there fire on GLOBAL stop and cancel exits
SCENARIO: WAITING_FOR_SIGNATURE's exit action enqueues "reminder SMS with signing link", written for the normal path to WRAP_UP. The caller, still on the line, says "cancel it, don't contact me." The cancel_or_rescind GLOBAL exit leaves WAITING_FOR_SIGNATURE, the exit action runs during run-to-completion, and the turn commits, so the outbox drains. The caller's phone buzzes with "Tap to sign your solar agreement" seconds after they cancelled.
WHY IT BREAKS: The invariants are stated over transitions. Effects hidden in entry and exit behaviors fire on every edge across the boundary, including the GLOBAL ones nobody wrote with that action in mind. Texting after an opt-out or revocation violates the TCPA revocation rules (47 CFR 64.1200(a)(10), effective April 2025), and "committed turn" doesn't distinguish a stop turn from a sale turn.

## A10
TOPIC: Untimed model checking can't state or prove deadline properties, so the graph is "verified" while hard time limits are broken
SCENARIO: The checker abstracts time: `after(n)` becomes a nondeterministic event. Required properties are timed: hang up within seconds of a stop; leave no live call unanswered beyond the abandonment threshold; let the OTP expire before a resend; end the call before a quiet-hours boundary in the called party's zone. A call at 8:58 pm enters READ_BACK, which takes 4 minutes. The untimed model happily allows "calling-hours guard checked at dial, call continues" to run past 9:00 pm into COMMIT and the SMS at 9:03 pm.
WHY IT BREAKS: Calling-hours guards sit at pre-dial. An untimed graph can't express "no sales fragment after 9 pm local", only orderings, so the time-boundary violation is invisible to the proof. TCPA hours run 8 am to 9 pm local to the called party (47 CFR 64.1200(c)(1)), and Florida's limit is stricter (Fla. Stat. 501.616: 8 am to 8 pm).
