## A1
DEFENSE: The scenario cannot get a lease figure spoken without a typed financing row: R180 types every financing row (loan, lease, PPA, PACE), so the lease fragment is already known to be a lease at build time. R91 puts every number behind a policy-table key, R32 allows only "non-triggering financing language before a quote" plus a "representative fully-disclosed example", and R85 READ_BACK covers financing terms. The gap is real but narrow: the co-occurrence lint is keyed to Reg Z terms only. Because the lint already runs "on every rendered reply" and the row type is known, adding Reg M's trigger set is a table change, not a redesign. A hang-up can't split the disclosure if it sits in the same mandatory segment (R39 playout marks).
EXISTING ELEMENTS: R180 financing-row typing build check; R32 Reg Z co-occurrence lint on every rendered reply, non-triggering language before quote; R91 no literal numbers, fact tokens are table keys; R85 READ_BACK financing terms; R39 mandatory segments and playout marks; R18 banned-claims lint.
NEW HARDENING: NEW: (1) A per-type advertising-rule registry. Every typed financing row must name its rule set (Reg Z for credit; Reg M 12 CFR 1013.7 for leases under the dollar ceiling; state lease-advertising rules), or the build fails. (2) A Reg M co-occurrence lint: any lease fragment that renders a payment amount, "$0 down" or another down-payment phrase must render, in the same mandatory segment, "this is a lease", total due at signing, number and period of payments, and security deposit, plus end-of-term liability where it applies, all from policy-table keys. (3) Lease payment amounts can't be spoken before QUOTE, and a hang-up mid-segment logs the disclosure as undelivered (R39), which sends a written disclosure through the outbox.

## A2
DEFENSE: The fragment in the scenario fails the build. R18's banned-claims lint bans "free/no-cost" wording, and R222 extends that lint to policy-table row text, so a promo row reading "EV charger free" can't be cited at all. R37 allows concessions only from a versioned pricing policy keyed on verifiable facts with a margin floor, never ad hoc. R199's quantifier lint requires a table key for aggregate claims. A rewording such as "included at no extra charge" hits the same no-cost ban. The remaining gap is a bundle with no "free" word over a padded price. That is a pricing-integrity problem rather than a free-claim problem, and the forward-only table (R140) already keeps the price history needed to detect it.
EXISTING ELEMENTS: R18 banned-claims lint (free/no-cost); R222 lint extended to policy-table row text; R37 versioned pricing policy, margin floor; R199 quantifier/aggregate lint; R140 forward-only policy table with tombstones; R92 substantiation ids.
NEW HARDENING: NEW: (1) Promo rows are typed, and a promo that bundles an add-on must cite the base price row it rides on. A build check over the forward-only table history blocks the promo if that base row rose within the prior 30 days or rises while the promo is live (the 16 CFR 251.1 regular-price test). (2) Any bundled add-on needs an unbundled price row, so "is it cheaper without it?" gets a true deterministic answer. If the prices are identical, the bundle may not be framed as a giveaway in any wording. (3) Promo-plus-price pairs are a claims-audit item.

## A3
DEFENSE: The objection fragment is blocked twice over. First, "offset that" is a savings/payment comparison, and R72 allows savings or comparison wording only with calculator_output provenance plus a substantiation id. A referral reward is a promotions key, not calculator output, so the lint rejects the filling. Second, "I can't afford $180" is an affordability fact. Under R71, suitability facts are qualification slots, never objection events, and the lint bans rebutting them. R150 then requires the financed payment to be at or below the calculator-verified savings band, or else NOT_SUITABLE/cash-only. R37 bans concessions triggered by objections, and R74 limits referrals to a self-opt-in link. Even so, no rule yet bars the reward as an inducement, so I harden that.
EXISTING ELEMENTS: R72 savings/comparison wording only with calculator_output + substantiation id; R71 suitability facts never objection events, lint bans rebuttal; R150 payment <= verified savings band else NOT_SUITABLE; R37 no concession from objection counts; R74 referrals only via self-opt-in link; R220 referral fragments tagged marketing.
NEW HARDENING: NEW: (1) Referral-reward keys get a regulation-profile row (CA B&P 7157 and state referral-selling statutes). A model-checked invariant makes any referral-reward fragment unreachable before SALE_SIGNED plus the end of the cancellation window. Afterwards it may only go out as a separate outbox message, and in banning states it is never sent. (2) A lint bans any fragment that pairs a payment or affordability key with a reward or promo key. (3) An "afford" lexicon row routes to the R150 suitability check, never to OBJECTION_HANDLING.

## A4
DEFENSE: The attack assumes removing a SKU needs a weeks-long bundle recertification. It doesn't. R140 took the policy table out of the bundle's rollback: it is forward-only, "recalled or withdrawn rows become tombstones no bundle can cite", and the runtime refuses any row outside its effective window. When a cited row is tombstoned, QUOTE and READ_BACK drop to lead-gen or callback fallback the same hour, and rollback can't resurrect the row. R160 adds a supply-status field that expires SKUs and a WAITING_FOR_BOM_MATCH gate that blocks install on any change. R178 sets the pattern for external feeds: a daily pull with a stale feed failing closed. The real gap is that no recall feed triggers the tombstone.
EXISTING ELEMENTS: R140 forward-only table, tombstones, effective_from/until enforcement, fallback to lead-gen/callback; R160 supply-status field, WAITING_FOR_BOM_MATCH, no-penalty cancel; R178 daily external feed, stale fails closed; R220 SERVICE profile with marketing fragments unreachable; final plan "certificates expire when a cited policy row changes".
NEW HARDENING: NEW: (1) A recall feed (CPSC recalls API plus manufacturer and UL bulletins, pulled daily and failing closed for battery/inverter rows) sets supply_status=recalled, which tombstones every product, warranty and fragment key for that SKU. (2) Pre-dial suppression: any marketing campaign aimed at owners of a recalled SKU (from install serial records) is refused. Those owners get only a SERVICE-profile recall notice (R220). (3) A signed but uninstalled contract with the SKU is held at BOM match and gets a no-penalty cancel. (4) A model-checked invariant: no QUOTE or upsell path cites a recalled SKU.

## A5
DEFENSE: "Earn up to {vpp_annual}" can't be certified. A third-party tariff rate that changes yearly is an "assumption" provenance row under R157, so any fragment filled from it must carry the lint-enforced "estimate, assumes X, not guaranteed" qualifier, and the tariff-filing monitor expires the row. R155 incentive typing bars capped or program-dependent money from the quote. R18 bans "guaranteed credits", and R199 requires a table key for aggregates. Backup is also covered: R83 stated-need slots (outage_backup) run deterministic product-fit rules, and every READ_BACK must carry the material-limitation rows. What's missing is a material-limitation row for third-party discharge control and a rule keeping enrollment off the sales call.
EXISTING ELEMENTS: R157 assumption provenance + qualifier lint + tariff-filing monitor; R155 typed incentive rows, "if approved, not guaranteed"; R83 material-limitation rows mandatory in READ_BACK, outage_backup product-fit rules; R18 banned claims; R199 quantifier lint; R161 warranty backing instrument.
NEW HARDENING: NEW: (1) VPP rows are typed third_party_program. Earnings fragments ("earn", "up to", annual amounts) are banned on the sales call. (2) Enrollment never happens on the call. It is offered only after PTO, by outbox, under the program's own terms and consent. (3) A material-limitation row is mandatory in READ_BACK whenever a battery is quoted: "utility programs may discharge your battery on event days and reduce backup". (4) A product-fit rule: outage_backup plus any program default flags a conflict, with an explicit correction. (5) The warranty row must state the throughput limits and whether program cycling counts against them.

## A6
DEFENSE: The calculator can't produce the savings figure the attack describes. R157 requires "the customer's exact tariff schedule ... on verified interval data, else no figure". R156 and R212 source usage and tariff_class only from the utility authorization API, which returns the customer's current NEM 2 schedule. R82 has existing_solar/existing_equipment suitability slots. R71 makes an unsuitable close Tier A harm and requires the success label to pass a sampled suitability audit. R220 types call_purpose, so an existing-customer upsell is its own campaign/bundle pairing. The gap is real: the calculator models the add-on, but not what the whole system loses if it crosses the expansion threshold.
EXISTING ELEMENTS: R157 exact tariff schedule else no figure, tariff-filing monitor; R156 verified_usage writers; R212 tariff_class from utility API; R82 existing_solar slots; R71 suitability table, Tier A unsuitable close, suitability audit; R220 typed call_purpose; R83 material-limitation rows.
NEW HARDENING: NEW: (1) A tariff_vintage slot (legacy tariff, interconnection date, grandfather end) read from the utility API and the interconnection agreement, never from speech. (2) Per-utility expansion_rule rows (e.g. CPUC greater of 10% or 1 kW). (3) For existing_solar, the calculator computes the whole-system delta, including lost legacy-tariff value through the grandfather end. Size is capped at the threshold, or the result is NOT_SUITABLE when the delta is negative, and there is no figure when the vintage is unknown. (4) A mandatory READ_BACK row when the add-on crosses the threshold: "this moves your system to {successor_tariff}". (5) Upsell campaigns stay lead-gen until this profile is certified.

## A7
DEFENSE: The invariant is misread. R46 says "all options to all, non-protected keys only". The product-policy table may legitimately branch on non-protected keys, and property jurisdiction is the clearest example. Matched-pair fair-lending tests vary only the prohibited-basis attributes ("prohibited-basis field tags") while holding jurisdiction fixed, so a per-state menu breaks nothing. R47 already gates by jurisdiction profile (lead-gen-only states). R178 conditions QUOTE on the property's jurisdiction, and R180 types every financing row, including PPA. The genuine gap is narrower: no row says which financing types are lawful in each state or utility territory.
EXISTING ELEMENTS: R46 product-policy table, non-protected keys only, prohibited-basis field tags, matched-pair tests; R47 jurisdiction profiles; R180 financing-row typing; R178 jurisdiction-keyed QUOTE invariant; R70 most-restrictive candidate set; R222 per-jurisdiction legal attestation field.
NEW HARDENING: NEW: (1) A product_legality row per (financing type, state, utility territory), each carrying the R222-style legal attestation and defaulting to deny. A PPA or lease row is reachable only where an attested legality row exists (e.g. no third-party PPA in Florida). (2) A model-checked invariant: QUOTE offers exactly the legal set for the property's jurisdiction, identically for every caller there. (3) Matched-pair tests are stratified by jurisdiction, so the fairness claim reads "same lawful menu within a jurisdiction".

## A8
DEFENSE: The design never treats one "Yeah" as consent. R144 turned the commit into an action-production prompt ("please say 'send the contract'") with an R77/R87 lexical gate. R85 makes READ_BACK state refund/cancellation policy and financing terms. R45 means the voice channel never takes payment. R223 requires a processor-page authorization that states amount, dates and number of debits, with the account holder's E-SIGN signature, so no card or ACH on file is created by voice. R216 makes CANCEL a saga with per-party substates. R91 bans unqualified term words. But a renewing plan bundled inside the product line would still ride on a single commit, so I close that.
EXISTING ELEMENTS: R144 action-production commit prompt; R77/R87 lexical commit gate; R85 READ_BACK cancellation/refund terms; R45 no voice payment; R223 written debit authorization; R216 CANCEL saga; R91 term-word lint; R120 ESIGN consent.
NEW HARDENING: NEW: (1) Recurring or auto-renewing service rows are typed negative_option. A build check bars them from any voice QUOTE or READ_BACK, so they are never sold on the call. (2) They are offered only after install, in writing, through an ARL/ROSCA flow: clear and conspicuous terms, a separate affirmative checkbox and signature, an acknowledgment email, and an online cancel path. (3) cancel_or_rescind gains a target (contract | plan), and the saga can cancel only the plan. (4) A lint bans "renews" tokens in voice fragments.

## A9
DEFENSE: The scenario contradicts the graph. R71 defines ROOF_FIRST as "inspection before any quote", so the agent can't quote a "Roof + Solar" SKU in that branch. R159 makes reroofing and panel work survey-driven change orders, each with a new quote hash, written re-disclosure and fresh e-sign. R178 adds a model-checked invariant: no QUOTE, READ_BACK, CONTRACT_SENT or install effect unless the installer's licence row is valid for the property's jurisdiction. R217 requires a per-profile home_improvement_contract with keyed fields. The real gap is that the licence row checks status per jurisdiction, not trade classification per line item.
EXISTING ELEMENTS: R71 ROOF_FIRST (inspection before any quote); R159 change orders with re-disclosure and fresh e-sign; R178 installer_license rows, daily feed, QUOTE/READ_BACK/CONTRACT_SENT invariant; R217 home_improvement_contract row; R179 storm-window ROOF_FIRST rows.
NEW HARDENING: NEW: (1) Every quote line item (array, roof, service-panel/EV circuit, trenching) carries required_license_class per jurisdiction (e.g. CA C-46, C-39, C-10, B). (2) The R178 invariant is extended so that each line item needs a valid matching class on the contracting licensee's row, or an attested state rule permitting it as incidental work. Otherwise the bundle is unreachable and is split into separately licensed contracts. (3) READ_BACK and the contract name the licensee and licence number for each line item, with separate lien and warranty rows for each.

## A10
DEFENSE: The urgency fragment can't exist. R78 has a lint that "bans fake urgency and unverifiable external-fact fragments". R153 requires a fixed fragment before READ_BACK, "There's no need to decide today.", which directly contradicts any deadline push. R15 sends defers_decision into the vulnerability counter, and R145 bounds indirect declines, so hesitation can't trigger a persuasion fragment. R92 allows social proof only as audited aggregates with substantiation ids, and R199's quantifier lint requires table keys. R151 bars optimizing variants on conversion. R116's WORM render log is our evidence too, and the R18 claims audit reviews it. Still, a rolling promo_end could pass a per-row check, so I add a history check.
EXISTING ELEMENTS: R78 fake-urgency lint; R153 "There's no need to decide today."; R15 defers_decision and vulnerability counter; R145 indirect_decline; R92 audited social proof; R199 quantifier lint; R151 no conversion-optimized variants; R140 forward-only table history; R116 WORM render log; R18 claims audit.
NEW HARDENING: NEW: (1) A build check over the forward-only table history rejects any promo whose terms were re-issued with a new end date within 12 months (rolling-deadline detector). (2) "Selected", "showcase", "limited spots" and deadline tokens are banned unless a typed finite_program row exists with counted inventory, decremented only by real install events, and with eligibility not based on street. (3) Deadline fragments are unreachable after any hesitation event. (4) The claims audit reviews deadline exposure across months.
