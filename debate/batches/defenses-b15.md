## A1
DEFENSE: The request is not "lost". GLOBAL is multi-label (R189): every safety event over its threshold fires, in a fixed order. So "delete my info and don't sell my number" fires stop/DNC, and that already writes the ledger. Anything unmatched falls to the root UNEXPECTED_EVENT handler and is logged (R52). Unmatched phrasings go to human review through the revocation intake bus (R115). R7 already makes deletion "a data operation, no retrain". Keeping the suppression record does not conflict with deletion. The TCPA and TSR require it, and CCPA exempts data kept for a legal obligation. The real gap: no event opens the CCPA clock.
EXISTING ELEMENTS: R189 multi-label GLOBAL; R52 root UNEXPECTED_EVENT; R115 revocation intake bus (human review of unmatched); R7 "deletion = data operation, no retrain"; R84 request_dnc_policy with outbox copy; R116 TSR WORM record set; R117 legal_hold
NEW HARDENING: Add a GLOBAL privacy_request(kind ∈ delete, know, correct, opt_out_sale_share, limit_sensitive) event, detected by lexicon and Needle. It co-fires with DNC and never replaces it. It plays a fixed acknowledgement fragment and its outbox effect opens a DSAR ticket stamped with a 45-day (or 15-business-day) due date, plus a written confirmation by SMS. After that, deletion covers every store except the TSR WORM set, legal_hold, and a hashed-number suppression entry. Extend the post-call sweep to privacy phrasings and add a Tier A red-team stratum.

## A2
DEFENSE: The design keeps very little about a person. Agents collect only coarse facts, never account, income or credit data (R7). There are no voiceprints (R118). Health spans are redacted, and only a type-less sensitive_exit label survives (R119). Dialect labels live only on audit records under surrogate IDs, never in CRM, and are deleted with the gold item (R131). Labeling audio is cut off from name and number and has a TTL (R143). Adverse outcomes already produce plain-language reason codes (R90 ADMT), so the inferences are enumerable. Verification also does not rely only on lead fields, because identity answers come from independent sources (R162). What is missing is the person-to-artifact index and a verification standard for requests.
EXISTING ELEMENTS: R7 data minimization; R118 biometric feature ban; R119 health-data quarantine; R131 surrogate-ID audit labels; R143 enclave, decoupling and raw-audio TTL; R90 reason codes; R162 independent identity sources; R141 print-and-mail outbox
NEW HARDENING: Add a subject-artifact registry. Every written artifact carries a session id, and only the DSAR service can resolve number/lead → sessions → manifest (lead record, slots with provenance, outcome, reason codes, the vulnerability/sensitive_exit flags, audit labels, transcripts, derived paraphrases), through a keyed surrogate map. For specific pieces, verification is an OTP to the verified number, plus a code mailed to the property of record, plus a signed declaration (7062). If verification fails, the request is downgraded to a categories response. A release check confirms that every artifact type is registered.

## A3
DEFENSE: The consent proof never lives only at the broker. The pre-dial gate requires a per-number PEWC artifact (timestamp, seller, disclosure version) in the seller's own ledger (R74), captured by an independent consent-capture provider (R162). The R116 TSR record set keeps "the consent artifact" for 5+ years in WORM storage. That is a legal-obligation retention, which a broker's DROP purge does not reach. A stale resold copy fails the gate if its artifact is not already in the seller's ledger. The Reassigned Numbers Database and internal DNC checks run at every dial (R73, R138). The one real gap is that a DROP request should mean "stop contacting me", and the design never hears about it.
EXISTING ELEMENTS: R74 per-number consent gate; R162 independent consent-capture provider; R116 TSR WORM consent artifact; R59 PEWC/warm-only dial list; R138 linearizable dial permit; R115 revocation intake bus; open item "lead-vendor consent audit"
NEW HARDENING: Lead intake accepts a lead only if its consent artifact is copied into the seller's WORM store at intake. Vendors must forward their DROP deletion notices, and each one is fed into the R115 bus as a suppression. A lead whose artifact the vendor has since purged, or whose duplicate arrives from another affiliate, is not dialed unless the seller-escrowed artifact matches. Vendor contracts must attest DROP processing dates.

## A4
DEFENSE: Disgorgement here would remove a labeler, not the product. Everything that speaks, prices, commits or complies is deterministic code. Needle only labels turns. Every state already has a deterministic fallback (callback or human, R2/R25), so destroying every weight sends calls to fallback and they keep running. Seed data is also narrow: historical calls "only seed the first graph" (R20), "teach caller intents only" (R18), and are PII-scrubbed (R7). Statistics and certification come from the disclosed agent's own calls. The pipeline already rejects transcripts that lack a retention-consent flag (R40). The real gap is per-source lineage: there is no certified model that avoids the seed data.
EXISTING ELEMENTS: deterministic fallback per state (R2, R25); R20 on-policy data; R18 intents only; R7 PII surrogates; R40 retention-consent flag rejection; R67 immutable retained bundles; R124 staged ramp; R135 equivalence re-keying
NEW HARDENING: Each release carries a source-lineage manifest, with content hashes per source plus a legal-basis/purpose record, and the build rejects any source without one. Each release also trains and certifies a "clean-room" variant on synthetic data and consented on-policy data only, with no seed transcripts, and keeps it as the standing disgorgement target. Seed sources need written legal review stating that AI training is within the original notice.

## A5
DEFENSE: The attack misreads two phrases. "Real data never replaced" (R33) means synthetic data never displaces real data. It is not a promise to keep real data forever. R7 says outright that "real utterances only in deletable gold sets; deletion = data operation, no retrain". Bit-identical replay is about inference determinism on the retained set, and R135 re-keys against whatever gold set is retained, so deleting an item does not break replay. Raw audio already has a retention TTL (R143). NO_RETAIN keeps nothing (R40, R113). The TSR set has its own defined 5-year retention period (R116). What is missing is a published per-category retention schedule.
EXISTING ELEMENTS: R7 deletable gold sets; R33 real-not-replaced (by synthetic); R135 equivalence re-keying on the retained gold set; R143 raw-audio TTL; R40/R113 NO_RETAIN; R116 TSR 5-year WORM; R119 health quarantine
NEW HARDENING: Publish a retention schedule per category (audio, transcript, labels, derived paraphrases, training union) in the notice at collection. The training union becomes a rolling window of real items (e.g. 24 months). Short NOT_SUITABLE and no-sale calls age out sooner. Canary audio comes only from staff recordings, consented recordings or TTS. A deletion removes the item and triggers a documented recount of rule-of-three for any state it affects.

## A6
DEFENSE: Much of this is already closed. Transcripts get surrogates before the big model sees them (R7). "Processors [are] barred from training on data" (R40). Labeling runs in an in-house or vetted enclave with VDI, no download and watermarking (R143), not on an open crowd platform. ASR is "prefer self-hosted" (R68), and vendor embedding settings are disabled (R118). Vendor contracts already carry forwarding duties (R115). Needle runs sandboxed with no network (R135). Still, the attack is right that live build-phase audio streams to vendors, and that the certificate pins ASR versions but not vendor terms.
EXISTING ELEMENTS: R7 PII surrogates before the big model; R40 processors barred from training, NO_RETAIN; R143 labeling enclave; R68 pinned and self-hosted ASR; R118 vendor embedding settings disabled; R115 vendor contract duties; preamble recording notice
NEW HARDENING: Put a vendor register into the certified bundle hash: each subprocessor has a 1798.140(ag)/7051 service-provider contract (no own use, no training, zero data retention, flow-down approval for sub-subprocessors). The build fails if any data flow goes to a vendor missing from the register. ASR must be self-hosted in all-party-consent states. The preamble names "our service providers, including AI services".

## A7
DEFENSE: Existing controls already cap exposure. Labeling is in-house or done by vetted staff in a VDI enclave, with no download, watermarking and access logs (R143). IDENTITY answers and address segments are muted, and audio is decoupled from name and number. No voiceprints or speaker embeddings are ever persisted (R118). The agent collects no account, income or credit data (R7). Credit facts come only from lender prequal (R90). Red-team work runs on generated scenarios. What is missing is formal Part 202 screening: ownership, employee location and subcontracting are not checked.
EXISTING ELEMENTS: R143 labeling enclave and muting; R118 biometric feature ban; R7 data minimization; R90 credit band only from lender provenance; R135 sandboxed inference; model-diverse red team (R97)
NEW HARDENING: Add a DOJ Data Security Program gate. Every vendor, subcontractor and employee with data access is screened for covered-person status, ownership and location. Processing stays in the US, and no subcontracting is allowed without approval. The CISA security requirements are implemented, with a bulk-threshold counter per data category, an annual audit and recordkeeping. External red-team crowds get only synthetic data, never real audio or slots.

## A8
DEFENSE: The design already does much of the Safeguards work. The lender runs the application and decisions. The voice channel never takes payment (R45). Lints ban SSN, DOB and bank requests (R89). Credit facts exist only as lender-verified provenance (R90). Labeling is enclave-only with access logs (R143). Needle has no PII store access (R135). Lead-gen mode already exists (R47). But the attack is right: arranging financing likely makes the seller a GLBA financial institution, and the compliance list names only Reg Z and ECOA.
EXISTING ELEMENTS: lender runs application and decisions; R45 no payment on voice; R89 SSN/DOB/bank lint; R90 lender-only credit provenance; R143 enclave; R135 sandbox; R47 lead-gen mode; R154 lender fee schedule
NEW HARDENING: Add a GLBA row to the regulation profile. The initial privacy notice goes in the e-sign packet and the outbox. Sharing NPI with nonaffiliated installers is blocked unless there is an opt-out or a 313.13 service-provider or joint-marketing contract, and a build invariant enforces this on the lead-gen handoff effect. Add a Safeguards program (Qualified Individual, MFA, encryption at rest, risk assessment, pen tests). The replay store keeps only lender reference tokens. The incident runbook sends the FTC notice within 30 days for 500 or more consumers.

## A9
DEFENSE: The training bucket is designed to hold little that can be notified. Surrogates go in before training (R7). Health spans are redacted (R119). No biometric templates are persisted (R118), so the voice-template element of the IL/TX/WA statutes does not apply. Audit audio is decoupled from name and number and has a TTL (R143). Dialect labels sit under surrogate IDs (R131). The TSR WORM set holds real numbers in separate storage (R116). But the attack is right that there is no record-level lineage, that paraphrases can leak details the scrubber missed, and that the surrogate map location is unspecified.
EXISTING ELEMENTS: R7 PII surrogates and audited scrubber misses; R119 health quarantine; R118 biometric ban; R143 decoupling and TTL; R131 surrogate IDs; R116 separate WORM store; R117 legal_hold
NEW HARDENING: Reuse the A2 subject-artifact registry with data-element tags (jurisdiction from the validated address, element classes) so a breach query returns the affected residents per state. The surrogate-to-real map lives in a separate KMS vault that is never co-located with the training bucket. Every big-model paraphrase is re-scrubbed, and an output with address or loan patterns is rejected. Run a yearly tabletop drill against the 30-day deadlines.

## A10
DEFENSE: The PREAMBLE is the right mechanism, and adding an element is one profile row. It is "compiled, unskippable" (R31). Its mandatory segments count only on uninterrupted playback (R39). It is built per regulation profile (R75) and already carries the recording notice, opt-out and ADMT notice (R90). Lead-gen mode is not an uncontrolled sale. The contract comes from the registered salesperson of record (R47). Outbound contacts and referrals happen only through self-opt-in (R74). The real gap: the CCPA notice-at-collection elements and a sale/share opt-out are not in the profile.
EXISTING ELEMENTS: R31 compiled unskippable PREAMBLE; R39 playout marks; R75 profile-required segments with position lint; R90 ADMT notice; R47 lead-gen mode; R74 self-opt-in referrals; R84 request_contact_info outbox
NEW HARDENING: Add a CCPA profile row: a short oral notice-at-collection segment (categories, purposes including AI training, sold/shared yes or no, retention, link) plus an outbox SMS with the full notice. A lint checks the segment against the 7012 element list. A GLOBAL opt_out_sale_share event is added. A build invariant blocks any lead-gen partner handoff unless the notice segment is playout-marked and no opt-out is set, or the partner is contracted as a service provider.
