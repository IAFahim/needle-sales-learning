
### Round 334. Winner: Designer
- Topic: History pseudostates resume a stale substate after a GLOBAL detour without re-running the guard that first admitted it
- Attack: In QUOTE.LOAN_TERMS the caller asks "who is this company again?" GLOBAL request_caller_identity plays the fixed answer, then returns to QUOTE through a (deep) history state, as is normal for detours. During the detour the caller also says "actually we're the Fresno house, not the Bay one", setting jurisdiction_changed. History re-enters QUOTE.LOAN_TERMS directly. The guard that chose LOAN_TERMS (lead-gen-mode false, financing allowed in this jurisdiction) was evaluated under the old jurisdiction and never re-runs. The agent quotes financing where only lead-gen mode is allowed. History restores where you were, not whether you may still be there. Entry guards are checked only on the original edge, so every detour-and-return is an unguarded entry. Invariants written as "edges into X require guard G" pass while history bypasses G. UML: history re-enters the last active substate, with no guard re-evaluation (UML 2.5 sec. 14.2.3.4.5).
- Defense: The design never uses history pseudostates. A detour is just the root handler: R192 requires that for every state and every GLOBAL event the effective handler is the root GLOBAL handler, checked on the enumerated binary relation (R134). In the scenario, the Fresno remark is itself a GLOBAL event. jurisdiction_changed is "fired on any stated residence change, validated or not" and "re-evaluates hour/attempt/disclosure guards -> WRAP_UP" (R70). R189 makes GLOBAL multi-label, so it fires alongside request_caller_identity, in a fixed order. R211(2) adds a second net: a property other than the lead's means "Are we talking about the home on <street>?" and, on a mismatch, lead-gen. R58 means one turn makes at most one transition, evaluated against the start-of-turn state. So no unguarded return to QUOTE happens in the same turn.
- Verdict: The design never specifies history pseudostates; GLOBAL events are root-handled (R192), and the residence remark is itself a GLOBAL jurisdiction_changed event that re-evaluates guards with unvalidated places added as candidates under most-restrictive-wins (R70, R189 multi-label). R47's lead-gen invariant is model-checked across all profiles, so any return path into a price state under a lead-gen profile would fail the check rather than pass vacuously.

### Round 335. Winner: Designer
- Topic: Timers live in user variables outside the graph, so a timer armed in one state fires after a GLOBAL exit into another
- Attack: StateSmith has no built-in timers; the usual pattern arms a timestamp variable on entry and checks it in a `do` handler. READ_BACK arms "silence > 6 s -> re-prompt: shall I send the agreement?" The caller says "my husband just collapsed", sensitive_event exits to the scripted exit. The timer variable is never cleared (READ_BACK's exit action doesn't clear it on this path). In the exit state, the shared `do` handler sees the expired deadline and plays the re-prompt: "Shall I send the agreement now?" The model checker explores control states and events. An armed timer is data, not a state, so a stale timer that leaks across exits is invisible to it. Every GLOBAL exit needs every timer cleared, and nothing checks that. That gap is exactly how a pitch line gets played into an emergency exit.
- Defense: Timers are not free-floating user variables here. Silence is a deterministic front-end event: "silence as deterministic events (no_speech_after_answer, silence(duration_bucket))" (R65). Waits are explicit graph substates: PAUSE, HOLD and WAITING_FOR_<effect> "with timer and handlers" (R55, with a build completeness check). An event is delivered to whatever state is current. Once sensitive_event has exited READ_BACK, a silence event lands in the scripted exit, which "no pitch" makes structurally unable to offer an agreement (R19). R193 events "carry a session epoch, and stale ones are dropped". Every utterance is a fragment certified by id, and R172's status-claim lint is keyed to state. So in our design a READ_BACK re-prompt fragment cannot be rendered from an exit state.
- Verdict: Silence is a deterministic front-end event delivered to whatever state is current (R65), waits are explicit graph substates with their own timers and a build completeness check (R55), and the mailbox drops stale events by epoch (R193). The attack's mechanism, a free-floating timestamp read by a shared `do` handler, is not how the design models time, and exit states play only scripted no-pitch fragments (R19).

### Round 336. Winner: Breaker
- Topic: Overlapping guards resolved by edge order: first-true-wins quietly picks the sale over the honest exit, and a diagram edit flips the order between releases
- Attack: The suitability table returns roof_age=24 (ROOF_FIRST condition) and move_horizon=18 months (NOT_SUITABLE condition). Both outgoing guards from QUALIFY are true. StateSmith takes the first by behavior order. In v14 a designer redrew the edges, and the order prefix changed from 1/2 to 2/1. ROOF_FIRST, which upsells a reroof plus solar, now beats NOT_SUITABLE for every caller who is planning to move. All invariants still pass, because both targets are "legal". The design checks invariants, not guard mutual exclusion or determinism. When guards overlap, the outcome is decided by a priority number edited in a drawing tool. Neither edge breaks a safety property, so the checker passes it, but the policy outcome flips with no test failing and no row changing in the suitability table.
- Defense: QUALIFY does not choose between ROOF_FIRST and NOT_SUITABLE with two overlapping graph guards. Per R71, the "versioned compliance-owned suitability table -> NOT_SUITABLE (honest polite exit, no rebuttal) or ROOF_FIRST" returns one outcome per call from the table. The graph switches on that single enum, so edge priority cannot flip the policy. The table is versioned, and "changing a row decertifies every branch that cites it". Unsuitable closes are Tier A harm in the per-call budget (R71), so a release that flipped the outcome would fail certification on audited real calls. The success label requires passing a sampled suitability audit. Also, R134 diffs the compiled (state, event, abstract-guard) relation against the exported graph, so a redrawn order shows up as a changed relation.
- Verdict: The design checks invariants over reachable states, not guard determinism: nothing requires outgoing guards at a choice point to be mutually exclusive, and R6 precedence applies to Needle event sets, not to graph guards. R71 says the table yields NOT_SUITABLE or ROOF_FIRST but defines no resolution when several rows match, and R134's diff compares the binary to the (already redrawn) exported graph, so a reordered diagram passes. The defense's closing elements (severity order, SMT exclusivity check, golden suitability regression) are all new.
- Fix: Give suitability rows a fixed severity order (NOT_SUITABLE > ... > ROOF_FIRST > OK) with the table returning the most severe match, and add a build check (SMT over the abstract guard domain) that outgoing guards at every choice point are pairwise exclusive and jointly exhaustive, so behaviour-order numbers can never decide an outcome; replay a golden suitability suite every release with compliance sign-off on any changed outcome.

### Round 337. Winner: Designer
- Topic: "Every commit passes READ_BACK" is true but insufficient: the commit gate keys on a question id that is constant across read-backs, so a yes to an old read-back binds new terms
- Attack: Read-back #1 says 7.2 kW at a total of $31,400. The caller asks "can we do the smaller one?" The machine backtracks, recomputes 5.8 kW and plays read-back #2. Midway, the caller barges in: "yes, yes, the one you said first." The COMMIT gate checks "short lexical affirm to this read-back question id". Both read-backs use the same fragment and question id, so the gate is satisfied. The slot store now holds 5.8 kW, so the envelope goes out for terms the caller explicitly rejected. The proven invariant is a path property: READ_BACK was visited. The property that matters is a data property: the affirm answers a read-back whose content hash equals the slot-store version that gets committed. Nothing ties the commit to which read-back instance it answers, so the invariant holds while the wrong terms get signed.
- Defense: The commit is bound to content, not just to having visited READ_BACK. R23: "Read-back bound to config hash; any change after read-back forces a new read-back." R49: "accept_offer commits only the quote hash read back immediately before the yes". R134 adds an independent outbox monitor that refuses CONTRACT_SENT unless the trace has READ_BACK "with a playback-engine completion mark for the same quote hash". In the scenario, read-back #2 was interrupted: mandatory segments count only on uninterrupted playback (R39). The commit question plays only after the last segment (R106), and AWAIT_* is entered only when it finishes (R14). So there is no open question to affirm. "Yes, yes, the one you said first" also fails the short direct-affirm check (R81), and R144 makes the commit prompt "say 'send the contract'".
- Verdict: The commit is already bound to content: read-back is bound to the config hash (R23), accept_offer commits only the quote hash read back immediately before the yes (R49), affirms carry the target question id (R58), and the independent outbox monitor refuses CONTRACT_SENT without a playback completion mark for the same quote hash (R134). An interrupted read-back #2 has no completion mark (R39, R14), and "yes, the one you said first" fails the short-direct-affirm check (R81) and routes to the reference resolver (R4).

### Round 338. Winner: Designer
- Topic: Counters reset on state entry plus data abstraction in the checker mean "clarify once, then fallback" and the call budgets never fire across a two-state ping-pong
- Attack: The clarify counter is a per-state variable zeroed in the entry action. The caller's turns alternate between "what?" (QUOTE -> CLARIFY_PRICE) and a dispute_prior_statement detour (re-read the table value, return to QUOTE). Each return re-enters QUOTE and zeroes the counter. The turn budget counts only LOCAL turns, and detours are GLOBAL. For 40 minutes the agent re-reads the price. It never falls back or wraps up, and the caller keeps getting pitched. Model checkers make slot data tractable by abstracting counters away or bounding them, so a counter that never reaches its limit shows up as at most a spurious, dismissed loop, never as a liveness violation. "Every call eventually reaches WRAP_UP" is then proved over an abstraction in which counters always count up.
- Defense: The premise is not our design. R69 counters are "total turns, per-state visits, backtracks, repeated objections, wall-clock -> WRAP_UP". Total turns and wall-clock count every turn, GLOBAL detours included. Per-state visits catches the ping-pong by counting re-entries into QUOTE and CLARIFY_PRICE, and no entry action zeroes them. dispute_prior_statement is a backtrack-class event, so the backtrack counter climbs too. "Clarify once, then fallback" is a call-level rule, and repeated unclear() feeds the vulnerability counter -> NO_SALE_SAFE_EXIT (R15). The design already anticipates the abstraction gap: "slot abstraction for model checking audited against live calls" (R49), plus property-based random walks over loops. R132's label-free monitors (clarify rate, CUSUM) would flag a 40-minute call.
- Verdict: R69's budget counters already include total turns, per-state visits, backtracks and wall-clock, so a 40-minute ping-pong hits the wall-clock and visit limits regardless of any per-state clarify counter reset. R49 audits the slot abstraction against live calls and runs random walks over loops.

### Round 339. Winner: Designer
- Topic: GLOBAL exit sequences are not absorbing: root handlers stay live inside the stop/cancel exit, so a second GLOBAL event re-routes an opt-out back toward sales
- Attack: The caller says "stop calling me." The stop/DNC exit is a short sequence of states under the root: confirm opt-out, outbox copy, goodbye. Mid-confirmation the caller asks "wait, who is this, is this a real person?" Root request_caller_identity fires (the most general handler), plays the fixed answer and then returns by history to the last sales state, QUOTE. The pitch resumes after a recorded opt-out. Equally, "let me talk to someone" inside the exit triggers request_human, a warm transfer to a closer. The checked invariant is "stop reaches the exit". It is not "after stop, no sales state or transfer to sales is reachable". Exit states inherit the root's GLOBAL transitions like any other state. An opt-out followed by more selling is a revocation violation under the TCPA and TSR (47 CFR 64.1200; 16 CFR 310.4(b)(1)(iii)(A)).
- Defense: "No pitch after decline" is already a model-checked whole-graph invariant (R21), and it is exactly the "after stop, no sales state reachable" property. A stop is not a pausable sequence either. Tier 1 stops "end immediately" (R24). The DTMF stop does "DNC write, fixed confirmation, hang up" (R75), and leave_taking "hangs up, with no question and no pitch" (R164). R189 orders the DNC write first, and "any transfer carries the DNC flag and is service-only". So request_human inside the exit cannot reach a closer. R138's dial permit reads the DNC ledger. A history return to QUOTE would also violate R21, which is checked on the compiled relation (R134).
- Verdict: "No pitch after decline" is already a whole-graph model-checked invariant (R21), Tier 1 stops end immediately (R24), the DTMF and leave-taking paths are confirm-then-hang-up (R75, R164), and R189 orders the DNC write first and makes any transfer service-only with the DNC flag. A return to QUOTE after a stop would break R21 on the checked relation (R134).

### Round 340. Winner: Designer
- Topic: Vacuous passes after a graph refactor: properties written against state names stay green when those states are split, renamed or bypassed
- Attack: The spec says "AG(in COMMIT -> previously READ_BACK)" and "commit tools only enabled in COMMIT". In v15 COMMIT is split into COMMIT_CASH and COMMIT_LOAN for a new lender, and QUOTE gains a fast path straight to COMMIT_LOAN. The old properties still name COMMIT, which is now unreachable, so both hold vacuously. CI shows all invariants passed. COMMIT_LOAN enables the e-sign tool with no READ_BACK on the fast path. Model checkers report a property as satisfied when its antecedent is never reached, unless vacuity checking is turned on. The property list is hand-maintained, while the graph changes every release. No check says "every state with a commit tool is covered by a property", so the safety of each release depends on someone remembering to rename strings.
- Defense: The key safety check does not depend on state names. R134's independently written outbox monitor "refuses CONTRACT_SENT or any commit effect unless the committed trace contains READ_BACK with a playback-engine completion mark for the same quote hash". It keys on effects, so a fast path to COMMIT_LOAN gets refused at the outbox. Tool exposure is generated, not hand-named: "tool lists derived from handlers (build fails on offered-but-unhandled)" (R52), and "commit tools exist only in post-read-back states" (R27). R85 phrases the invariant as "every path to any commit state", meaning a class, not a string. Matched-pair tests, random walks (R49) and Tier A certification on real calls cover any new state. A split state starts uncertified and runs on fallback.
- Verdict: The decisive safeguard is not a name-based property: R134's independent outbox monitor refuses any commit effect unless the committed trace holds a read-back completion mark for the same quote hash, so a fast path to COMMIT_LOAN is blocked at the outbox. Tool lists are derived from handlers (R52) and new states start uncertified on fallback (R3).

### Round 341. Winner: Designer
- Topic: An `else` / default branch on a choice point fails open when the policy table gains a value the graph was never generated for
- Attack: A suitability choice point covers roof_material values ASPHALT, TILE and METAL, with a mandatory default `else -> QUOTE`. Ops adds SLATE_REQUIRES_ENGINEERING and WOOD_SHAKE_FIRE_ZONE to the versioned policy table. The table's certificate expires and is reissued, but the graph is not regenerated. Every slate or wood-shake roof falls through `else` straight to QUOTE. These are fire-zone homes that should have gone to NOT_SUITABLE or an engineering review. The model check of the unchanged graph still passes. The graph and the policy table are versioned separately. Guards switch on enumerations the table owns, and nothing checks that the switches are exhaustive against the current table. A default branch written for "unusual but fine" silently takes every new category, including the dangerous ones. The checker treats `else` as a legal edge, so this release-time mismatch never shows up.
- Defense: The graph and the table can't silently drift apart. The facts table is in the certified bundle, and "certificate = (state, weights hash, facts-table version)" (R3). "Changing a row decertifies every branch that cites it", and certificates "expire when a cited policy row changes". Adding SLATE/WOOD_SHAKE rows expires QUALIFY's certificate, so it runs on deterministic fallback. Reissuing a certificate means replaying gold sets under the new table (R3). R140 continuously re-checks bundles "as compatible with that table" (lints, fact-key coverage); otherwise QUOTE/READ_BACK "drop to lead-gen or callback fallback". The suitability decision itself comes from the table (R71), not from a graph switch on roof material.
- Verdict: Under R71 the suitability decision is an outcome produced by the compliance-owned table, not a graph switch on roof material, so a new SLATE or WOOD_SHAKE row carries its own outcome. Certificates are keyed on the facts-table version and must be re-earned by gold replay (R3), and R140 drops QUOTE/READ_BACK to fallback when a bundle is not compatible with the current table.

### Round 342. Winner: Designer
- Topic: Exit and entry actions run on every path across a state boundary, so effects placed there fire on GLOBAL stop and cancel exits
- Attack: WAITING_FOR_SIGNATURE's exit action enqueues "reminder SMS with signing link", written for the normal path to WRAP_UP. The caller, still on the line, says "cancel it, don't contact me." The cancel_or_rescind GLOBAL exit leaves WAITING_FOR_SIGNATURE, the exit action runs during run-to-completion, and the turn commits, so the outbox drains. The caller's phone buzzes with "Tap to sign your solar agreement" seconds after they cancelled. The invariants are stated over transitions. Effects hidden in entry and exit behaviors fire on every edge across the boundary, including the GLOBAL ones nobody wrote with that action in mind. Texting after an opt-out or revocation violates the TCPA revocation rules (47 CFR 64.1200(a)(10), effective April 2025), and "committed turn" doesn't distinguish a stop turn from a sale turn.
- Defense: Effects in this design are never fired directly. They are intents appended to the outbox and "drained only on committed turns" (R13). The outbox has its own gates. R149 extends "the consent gate to every outbound SMS and email". R189 handles a multi-intent turn in a fixed order: "DNC write, then cancel", so the DNC/cancel record exists before the turn commits. R122 makes registration an outbox guard. R216 makes CANCEL a saga with an invariant against further action while a cancel is open. R173 says a cancel hit voids the envelope through the vendor API. R196's SMS budgets add another check. The reminder intent reaches a drain that sees a revoked contact and refuses it.
- Verdict: Effects are only outbox intents drained on committed turns (R13), and the drain is gated: consent gate on every SMS (R149), DNC write ordered before cancel in the same turn (R189), SMS guards and budgets (R122, R196), and the cancel saga plus envelope void (R216, R173). A reminder intent from an exit action meets a revoked contact at the drain.

### Round 343. Winner: Designer
- Topic: Untimed model checking can't state or prove deadline properties, so the graph is "verified" while hard time limits are broken
- Attack: The checker abstracts time: `after(n)` becomes a nondeterministic event. Required properties are timed: hang up within seconds of a stop; leave no live call unanswered beyond the abandonment threshold; let the OTP expire before a resend; end the call before a quiet-hours boundary in the called party's zone. A call at 8:58 pm enters READ_BACK, which takes 4 minutes. The untimed model happily allows "calling-hours guard checked at dial, call continues" to run past 9:00 pm into COMMIT and the SMS at 9:03 pm. Calling-hours guards sit at pre-dial. An untimed graph can't express "no sales fragment after 9 pm local", only orderings, so the time-boundary violation is invisible to the proof. TCPA hours run 8 am to 9 pm local to the called party (47 CFR 64.1200(c)(1)), and Florida's limit is stricter (Fla. Stat. 501.616: 8 am to 8 pm).
- Defense: The time guarantees don't rest on the untimed proof. The design enforces them in deterministic runtime code. R69's counters include "wall-clock -> WRAP_UP". Stops "end immediately" (R24), within ten seconds. The abandonment threshold is a per-call measured invariant: "first PREAMBLE segment starts within about 1.5 s" plus a 30-day counter (R109, R142). R139 gives the dial gate pinned tzdata, authenticated time and a guard band. R70 and R183 re-evaluate hours guards mid-call on a jurisdiction or location change. The R122 outbox guard treats texts as solicitation, and R149 gates every SMS. Note that 64.1200(c)(1) governs initiating solicitations, so a 9:03 pm SMS is a new initiation and gets its own guard.
- Verdict: Time limits are enforced by runtime code rather than claimed by the untimed proof: wall-clock budget to WRAP_UP (R69), immediate stop handling (R24), per-call preamble deadline and abandonment counter (R109, R142), and a dial gate with pinned tzdata, authenticated time and a guard band (R139). The hours rules govern initiating solicitations, so continuing a lawfully started call is not the violation the attack claims, and later SMS go through their own outbox guards.
